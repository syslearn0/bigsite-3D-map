## 3. 決まっている前提

### 位置
- ホールの中では GPS はほぼ効かない。ブラウザの位置情報は Wi-Fi なども混ぜるので、屋内で 5〜20m くらい。
- **ホール単位までは自動、島から先は地図のタップで決める**。机1つ（0.9m）は位置情報では分からない。
- 西・南は同じ場所の上下に別のホール（1F／4F）があるので、階は利用者が選ぶ。

### 電波
- 携帯各社は毎回大きな対策をするが、開場前の待機列や昼は混む。
- 地図・机の配置・自分の印は**すべて端末の中で動く**。通信が要るのは、共有する情報（協力者の入力、有志の情報）だけ。

### 形
- 冬コミまでは Web（PWA）。直してすぐ届く、URL で渡せる、iPhone・Android を1つで作れる、ストア審査で止まらない。
- Bluetooth で周りに知らせる・気圧で階を判定する、などが要るようになったら、Capacitor で包んで Android アプリにする。

### 規模
- 数千人規模なら、サーバーの負荷は問題にならない（地図と配置は固定ファイルで配る。共有の情報だけ外部サービス）。
- 重いのは人の仕事：開催ごとの配置の入れ直し、有志の情報の見回り、運営との関係。

## 4. データ

### 4.1 出典と使える条件
| データ | 使い方 | 条件 |
|---|---|---|
| OpenStreetMap | ホール・通路・まわりの建物・トイレの形と位置 | ODbL 1.0。出典を書く。作ったデータも同じ条件 |
| ビッグサイト主催者向け図面（白図） | 寸法・階・トイレなどの位置を**参考に**する | 規約は「施設の利用に関わる目的のみ・改変不可・商用不可」。**個人・非営利で参考にするのは構わない**とビッグサイトから返事あり。図面そのものは再配布しない（`data/private/` は git に入らない）。図面から作った形を公開版に含めてよいかは、念のため確認するとよい |
| コミケのカタログ・Webカタログ | 島の配置・サークル情報 | 準備会・Circle.ms の権利。**入れ方は準備会への問い合わせの返事を待つ** |

### 4.2 机の配置の形
`src/data/layout-sample.json` の `lines` が島の列（ブロック）1つずつ。エディタもこの形を書き換える。

```json
{ "hall": "E1", "block": "A", "start": [x, z], "angle": 0.78, "segments": [16, 16], "genre": "作品A" }
```
- 座標は会場の中のメートル（x：東、z：南）。`start` は島の中心線の始点、`angle` は島の向き
- `segments`：横切る通路で区切られた区間ごとの机の数
- 番号は A側を始点から進み、B側を戻る。机1つが番号1つ、左右の半分が a・b
- 計算は `src/lib/layout.ts`（`expandBooths`・`islandEnds`）

## 7. 技術

- Next.js 16（App Router）・TypeScript・three.js。公開は Vercel（main に push すると公開し直される）
- 画面は `src/components/VenueView.tsx` の1つ。机は数が多いので InstancedMesh で描き、上からの見方の番号は2D の canvas を重ねて描く
- 会場データ：`npm run fetch:osm` → `npm run build:venue`（`src/data/venue.json`）。見本の配置：`npm run build:layout`
- テスト：`npm test`（配置番号の重なり・机がホールの中か・番号の付け方・端の番号）
- 開発サーバー：`npm run dev`（Windows の PowerShell では `npm.cmd run dev`）
- オフライン：`public/sw.js`。開発中は登録しない。本番ビルドで確かめる
